# TASK 16318 — literal brief (investigate the agent's usage-limit handling; do not guess)

Issue: https://github.com/tangency-labs/solidcraft/issues/16318

## The report

Title: "AI Agent Does Not Resume After Usage Limit Resets".

"When using Claude as the AI agent in SolidCraft, I sometimes reach the agent's usage
limit before it finishes executing a task. The agent stops and displays:

    Internal error: You've hit your 5-hour limit · resets 6:30pm (America/New_York)

The problem is that once the usage limit resets, the agent does not automatically
resume the interrupted task. Expected: after the limit resets, the agent should be
able to resume the interrupted task from its previous state. Actual: the agent stops
when the limit is reached and remains interrupted even after the limit resets."

Steps to reproduce: use the $20 Claude plan, start an agent with a long enough prompt
that it consumes the 5-hour limit.

The upstream maintainer (raykholo) triaged it: "This is new: the Assistant panel does
not keep a task to continue after the provider's usage limit resets, and the limit
message in your report comes from the agent's provider."

## WHAT YOU MUST DO — exactly this

1. FIND THE AGENT LOOP AND ITS ERROR HANDLING. The Assistant panel and the agent
   loop live in the repository: look for `crates/ui-egui/src/agent_chat/`, the
   `crates/agent/` crate, and the place where a provider error becomes an
   "Internal error: ..." message. Grep for `Internal error`, for the provider error
   text, for how a turn ends and what the panel keeps afterwards.

2. THE QUESTION TO ANSWER: what does the agent keep when a turn ends with a
   provider error? Specifically:
   - is the TASK (the conversation and the work already done) kept, or is it dropped
     when the turn fails?
   - is there a way to CONTINUE an interrupted task from the panel?
   - is the provider's "usage limit" error distinguishable from other provider
     errors (a retryable one vs a fatal one)?

3. THE FIX, if there is one that does not depend on the provider:

   The report asks for two things: (a) the task is PRESERVED when the limit is hit,
   and (b) it can be RESUMED afterwards. The part that is ours and testable without
   a paid subscription is (a) and the plumbing of (b): the panel must keep the task
   and offer to continue it when the agent is available again, instead of the task
   disappearing or the panel being stuck.

   Write the test FIRST, in the area's EXISTING test file (the agent chat's own test
   file — look for `crates/ui-egui/src/agent_chat/` tests and the `crates/agent/`
   tests; use the file that already holds the panel's behaviour tests). The test
   must FAIL before the fix: a provider error that says the limit was hit must leave
   the task resumable, exactly as the panel does for an interrupted turn.

4. IF the fix would need the PROVIDER to tell us when the limit resets (a timer, a
   polling API), that is NOT ours to implement: the message only carries the reset
   time in its text. So the fix must work with what we get: the error arrives, the
   task is kept, and the user can continue it. Implement THAT, and say in the
   commit/report what is and is not automatic.

5. IF YOU CANNOT REPRODUCE IT, DO NOT invent a fix and DO NOT open a pull request.
   Report what you ruled out. (A provider error can be simulated in a test with a
   fake provider: look at how the agent tests fake a provider response.)
