# TASK 16460 — literal brief (investigate with a reproduction; do not guess)

Issue: https://github.com/tangency-labs/solidcraft/issues/16460

## The report

Title: "Can't select plane to start new sketch".

The reporter says: when MANY drawings (tabs) are open, starting a new Model and a
new Sketch FAILS WITHOUT an error because a plane cannot be selected. The expected
behaviour is "Plane should be selected".

The command context the app recorded:

    Could not build command parameters: "Select references to build from first"
    ConstructAuto {
        command: "construct.plane",
    }
    [
        SelInput {
            label: "ui.construct_auto.refs",
            accept: 33766,
            multi: true,
            places: false,
            tip: None,
            items: [],
        },
    ]
    {}

Note the empty `items: []`: the pick for the construction plane had NO candidates.

A second reporter (JamesMowery) confirms it on 0.41.0, Debian 13 + Niri + Wayland:
"It does not fix itself until restarting. However, this issue (if related) prevents
me from selecting any existing geometry as well." That second detail is the most
important clue: it is not only the plane, it is ANY geometry, and it does not
recover until the app restarts.

The upstream triage (raykholo) could NOT reproduce it on Linux and asked for a
video of the New Sketch step.

## What you must do — exactly this

1. FIND THE CODE PATH that produces that message. Search for the command that
   builds a construction plane automatically (`construct.auto`, `construct.plane`,
   the `ui.construct_auto.refs` label and the `SelInput` with `accept: 33766`),
   and the code that decides WHICH candidates the pick offers. The number 33766
   is a bitmask of what the pick accepts; find what it is made of.

2. REPRODUCE IT HEADLESS. The bug is about MANY OPEN DRAWINGS: the pick's
   candidates come from the active tab's world, and something about having many
   tabs open (or about switching between them) leaves that world empty or stale.

   `session_world`, the tab/document switch code, and how `app.session` and the
   per-tab world are swapped. Write a test in the area's existing test file that
   opens several designs (the test harness supports more than one — look at how
   the other tests that use several documents do it) and then tries to pick.

   The area's existing test file for the viewport picking is the one that holds
   the `Hit`/pick tests (search for the test file that exercises picking and the
   construction plane). Do NOT create a new test file.

3. If you CAN reproduce it, fix it, and the regression test goes in that same
   existing test file.
