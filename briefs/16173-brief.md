# TASK 16173 — literal brief (investigate the icon; do not guess)

Issue: https://github.com/tangency-labs/solidcraft/issues/16173

## The report

Title: "Task bar".

The reporter says: when SolidCraft is put on the Windows task bar, THE LOGO
BECOMES A GREY SQUARE. They report the same for another application.

Environment: Windows 11 x86_64, SolidCraft 0.40.1.

## What is already known about the icon (do not redo this)

* The Windows icon of the EXECUTABLE is
  `assets/icons/app/windows/exports/solidcraft-executable.ico`. It is embedded in
  the `.exe` by `apps/solidcraft/build.rs`, which writes a `1 ICON "solidcraft.ico"`
  resource line and compiles it with `embed_resource`. On a non-Windows target
  `build.rs` returns early, so nothing is embedded there.
* The `.ico` was built by `assets/icons/app/shared/source/windows_ico.rs`
  (`windows_ico::encode()`), which writes 7 entries: 16, 24, 32, 48, 64, 128 and
  256 pixels, each a 32-bpp DIB (not a PNG).
* The `xtask` that regenerates the exports is `xtask/src/app_icons.rs`
  (`cargo xtask icons`): it draws the PNG per size with `solidcraft-cli icon` and
  then writes the executable `.ico` with `windows_ico::encode()`.
* The installer's `.ico` is a different file
  (`assets/icons/app/windows/exports/solidcraft.ico`), built by `draw()` as a
  single 256 px PNG.

## What you must do — exactly this

1. LOOK AT THE ICON'S ACTUAL PIXELS. Decode the entries of
   `assets/icons/app/windows/exports/solidcraft-executable.ico` (a small Python
   script reading the ICONDIR and each BITMAPINFOHEADER is enough) and check
   whether the image is a real icon or a flat grey square. Look at EVERY size,
   not only the 32 px one: Windows picks the size it needs for the task bar, and
   a bad entry at one size shows up as a grey square while the others look fine.

2. COMPARE with the other exports of the same mark
   (`assets/icons/app/windows/exports/solidcraft.ico`, the Linux PNGs under
   `assets/icons/app/linux/exports/`) and with what `solidcraft-cli icon` draws
   (`cargo run -p solidcraft-cli -- icon --size 32 --out /tmp/i32.png`, then look
   at the PNG). If the `.ico` entries do not match what the CLI draws, the bug is
   in `windows_ico.rs` (the encoder) and that is what you fix.

3. Look at `assets/icons/app/shared/source/windows_ico.rs` closely: how it
   converts the drawn RGBA pixels into the 32-bpp DIB the `.ico` needs (the
   BGRA order and the AND mask that a DIB icon requires). A wrong channel order
   or a wrong mask can leave Windows showing the icon as a grey block.

4. The regression test goes in the area's EXISTING test file: the tests of
   `assets/icons/app/shared/source/windows_ico.rs` (the same file or the test
   module next to it) or the icons test of the `xtask`. Do NOT create a new test
   file. The test must assert something real about the encoded icon (for
   instance, that the decoded pixels of each size are not a flat colour, or that
   the entry has the sizes Windows asks for).

5. The gate: `cargo fmt --all` and the test of the crate that owns the icon
   code. Save the output to
   `/home/user/.local/share/solidcraft-orch/logs/16173-GREEN.log`.

If the pixels turn out to be a proper icon and the defect is elsewhere (the
Windows shell caching the old icon, or the way the shortcut is created), report
that with the evidence and open NO pull request.
