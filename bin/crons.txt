# The crons of the loop. THIS FILE IS THE SOURCE.
#
# WHY (2026-11-17): there were two graphs. workflow.yaml declared two crons
# (the pipeline and the gate queue) and README.md documented five. The
# declared graph and the executed graph were not the same thing, and
# nothing checked: a cron could exist, run every day, and be in neither
# list. The repo's own audit found the same shape in the process graph
# (reports/loop-codigo.md): two arbitrators for one concept, two
# directories, and a graph nobody ran.
#
# workflow.yaml says WHICH NODE each cron belongs to. bin/workflow-validate.py
# checks that this file and workflow.yaml agree, and that every script
# named here exists. A cron that is not in this file does not run, and a
# node whose cron_job is not here is a node nobody runs.
#
# FORMAT (one cron per line, '#' starts a comment):
#
#   <job> | <schedule> | <script> | <node> | <what it does>
#
#   <job>      the name of the job: its line in the crontab block and its log, logs/cron-<job>.log
#   <schedule> a 5-field cron expression
#   <script>   the script, relative to the repo root
#   <node>     the id of the node in workflow.yaml, or '-' when the cron
#              is a side job and not a step of the issue process
#
# A cron that is registered here but not installed on this machine is not
# an error of the graph: bin/preflight.sh says what is missing.
#
# ---------------------------------------------------------------------------
# LOS HORARIOS NO CAEN TODOS A LA VEZ (2026-11-20)
#
# POR QUE: cada corrida de un cron escribe en el state.db de hermes (la
# entrega de la salida, el registro de la corrida). Diez crons que caen en
# el MISMO minuto abren diez escritores a la vez sobre un SQLite de 256 MB, y
# el mutex de escritura se queda tomado segundos ("writer mutex
# unavailable ... held for 12.4s"). Con el mutex tomado, el bucle de eventos
# del gateway deja de responder, su watchdog lo mata ("missed 3 consecutive
# liveness probes ... exiting with code 75") y el supervisor lo reinicia: se
# van los crons, las sesiones de los agentes y sus turnos ("session turn
# lease lost"). El 20-11 el gateway se reinicio 6 veces y los turnos de los
# agentes se cortaron asi, sin que nada pareciera de memoria.
#
# COMO SE ARREGLA: cada cron tiene sus propios minutos y ningun par de
# crons cae en el mismo minuto. Y los crons que no necesitan ir rapido van
# mas lento: el que baja la prioridad de las compilaciones paso de cada 2
# minutos a cada 10, el estado del loop y la limpieza de disco de cada 15 a
# cada 30, y el guard del prompt de cada 5 a cada 15. Los que importan
# conservan su ritmo: la wave cada 10, la cola de gates cada 5 (minutos 3,
# 8, 13...), el pipeline cada 5 (minutos 2, 7, 12...), que ademas quedan
# DESPUES de la wave: la wave despacha a los :00, el pipeline encola los
# gates a los :02 y la cola los saca a los :03.
# ---------------------------------------------------------------------------
